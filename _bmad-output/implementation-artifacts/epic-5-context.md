# Epic 5 Context: Извлечение спецификации и маппинг с confidence

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Превратить текстовый артефакт загруженной сметы в структурированную спецификацию и сопоставить её со справочником расценок. Эпик закрывает середину конвейера smeta1: локальная LLM извлекает позиции (материал/работа, ЕИ, количество, раздел), сопоставление с расценкой и `confidence` выполняются в `rate-catalog`/`estimate`, а API ручной проверки позволяет подтвердить или исправить результат.

**As-built 2026-10-25:** `mapping-service` не реализован и удалён. Извлечение выполняет `spec-service` через `llm-proxy`; сопоставление — `rate-catalog` по эмбеддингам (Story 8.1), сохранение и ручная проверка — `estimate`. Это делает данные пригодными для детерминированного расчёта (Epic 6): расчёт опирается только на проверенные сопоставления и снапшоты, а не на вывод LLM. Полный UI валидации сознательно отложен до 1.1 — в MVP достаточно API.

## Stories

- Story 5.1: LLM-извлечение спецификации (local-first)
- Story 5.2: Маппинг со справочником и нормализация ЕИ с confidence
- Story 5.3: API ручной проверки маппинга

## Requirements & Constraints

- Вход — текстовый артефакт извлечённой сметы (результат pdf-extract), а не PDF напрямую.
- Извлечение формирует список позиций с полями: тип «материал/работа», ЕИ, количество, раздел сметы. Покрытие извлечения на типовых цифровых PDF ГРАНД-Смета/АВК-Смета — не ниже 95%.
- Инференс выполняется local-first через `llm-proxy` → `llm-gateway` на локальном CPU-only рантайме (GGUF q2–q3, 8 ГБ ОЗУ, без GPU). Облачный маршрут не применяется без явного согласия (`X-Allow-Cloud`, `LLM_ALLOW_CLOUD`/`LLM_ALLOW_CLOUD_FALLBACK`).
- **As-built 2026-10-25:** версий справочника нет; сопоставление идёт с ценой за точный регион/год/квартал/зону по cosine-эмбеддингу наименования.
- Каждой позиции присваивается `confidence` в диапазоне 0–1; позиции с `confidence < 0.70` помечаются как требующие проверки. Целевая доля таких позиций — не более 15% на тестовом наборе; калибровка порога на реальных PDF — после MVP.
- Целевое покрытие маппинга — 90–95% на тестовом наборе.
- API ручной проверки позволяет подтвердить или изменить сопоставление; выбранная расценка/ЕИ и статус позиции сохраняются. Низкоуверенные позиции выделяются в ответе API.
- Полный UI валидации маппинга в этот эпик не входит (1.1).
- Целевые объёмы: 100–500 позиций на смету, 20–50 смет в месяц; ориентир времени обработки при локальной CPU-only модели — 30–60 с.
- LLM не выполняет арифметику и не участвует в расчёте стоимости.

## Technical Decisions

- `llm-gateway` — единственная точка инференса с единым интерфейсом независимо от рантайма; политика local-first, запрет облачного fallback по умолчанию, режим `structure_only` и аудит событий (attempt/fallback/denied/allowed) живут внутри него. Вызывающие сервисы не реализуют эту политику самостоятельно.
- **As-built 2026-10-25:** `mapping-service` удалён. Сопоставление — `POST /v1/rate-catalog/matches` (pgvector) + `POST /v1/estimates/{id}/versions/{vid}/match-rates`; `confidence` — cosine score, статус остаётся `proposed`.
- Справочник и его цены читаются у `rate-catalog` через API; прямые запросы к чужой базе запрещены. Позиции смет и их снапшоты принадлежат `estimate`; подтверждённые данные фиксируются в позиции.
- Identity приходит только заголовками api-gateway (`X-User-Id`, `X-Company-Id`, `X-Role`); JWT сервисы не парсят. `company_id` обязателен, фильтрация — в репозитории; отсутствие identity означает отказ. Из бэкенд-сервисов наружу экспонируется только api-gateway; UI — отдельный фронтенд-контейнер.
- У каждого сервиса своя база в общем Postgres и собственные миграции Alembic.
- Конвейер: PDF → текст → LLM-спецификация → маппинг с confidence → ручная проверка → детерминированный расчёт. Очередь — `spec_job` в Postgres; контракт артефактов не зависит от транспорта.
- Конвенции: идентификаторы — UUID; время — ISO-8601 UTC; ошибки — RFC 7807 `application/problem+json`; списки — `limit`/`offset`; версия API — в пути (`/v1/...`); поля — `snake_case`; денежные суммы — Decimal, не float.
- Целевые сервисы: `smeta/spec-service/`, `smeta/llm-proxy/`, `smeta/llm-gateway/`, `smeta/rate-catalog/`, `smeta/estimate/`.

## UX & Interaction Patterns

- Сметчик видит по каждой позиции предложенное сопоставление, нормализованную ЕИ и уровень уверенности; проблемные позиции (`confidence < 0.70`) визуально/структурно выделены в ответе API, чтобы их можно было проверить первыми.
- Действия проверки: подтвердить предложенный маппинг либо выбрать другую расценку/ЕИ; результат фиксируется в позиции и становится основанием для расчёта.
- В MVP взаимодействие идёт через API; полноценный экран валидации появится в 1.1. Ошибки должны быть понятны пользователю и не раскрывать внутренние детали сервисов.

## Cross-Story Dependencies

- Story 5.1 зависит от текстового артефакта Epic 4 (структура строк/таблиц) и от локального рантайма `llm-gateway` из Epic 1.
- Story 5.2 зависит от результата 5.1 и от справочника Epic 3; импорт цен и эмбеддингов должен быть доступен до сопоставления (версий справочника нет).
- Story 5.3 зависит от предложений 5.2: без сохранённых позиций с `confidence` нечего подтверждать. Подтверждённые расценка/ЕИ и статус — вход для расчёта Epic 6.
- Снапшоты расценок/ЕИ (Epic 3, Story 3.3) фиксируются в позициях сметы при расчёте; маппинг обязан передать идентификатор расценки и нормализованную ЕИ, чтобы снапшот можно было построить без обращения к изменяемому справочнику.
- Простой UI Epic 7 отображает спецификацию, маппинг и стоимость; полный UI валидации маппинга — 1.1.
