# Epic 4 Context: Загрузка и извлечение цифрового PDF

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Реализовать входную точку конвейера smeta1: приём цифрового PDF-файла сметы, его валидацию и сохранение в MinIO, а затем конвертацию PDF в текст без OCR. Эпик обеспечивает надёжный и воспроизводимый текстовый артефакт со структурой строк и таблиц, на который опирается LLM-извлечение спецификации (Epic 5). Сканы и файлы сверх лимита отсекаются на входе с понятной ошибкой, поэтому неподдерживаемые данные не попадают в конвейер.

## Stories

- Story 4.1: Загрузка цифрового PDF в MinIO с валидацией
- Story 4.2: Конвертация PDF → текст (без OCR)

## Requirements & Constraints

- Принимаются только цифровые PDF с текстовым слоем; целевые источники — ГРАНД-Смета, АВК-Смета и совместимые по текстовому слою. OCR в MVP отсутствует.
- Максимальный размер PDF — 5 МБ; превышение отклоняется с понятной пользователю ошибкой.
- Файл без текстового слоя (скан) отклоняется как неподдерживаемый.
- Загрузка доступна только авторизованному пользователю; файлы и записи о них изолированы по компании.
- При успешной загрузке файл сохраняется в MinIO (S3), а в БД создаётся запись `file` с `storage_key`, `mime_type`, `size`, `meta`.
- Извлечение текста должно сохранять структуру строк/таблиц; допустимые библиотеки — pdfplumber или pypdfium2.
- Результат извлечения сохраняется как артефакт и передаётся следующему шагу конвейера; он не должен зависеть от конкретного брокера очереди.
- Покрытие извлечения на типовом тестовом наборе PDF ГРАНД-Смета/АВК-Смета — не ниже 95%.
- Целевые объёмы: сметы по 100–500 позиций, файлы ≤ 5 МБ; система рассчитана на 20–50 смет в месяц.

## Technical Decisions

- `pdf-extract` — отдельный FastAPI-сервис, отвечающий за валидацию цифрового PDF и конвертацию PDF → текст; хранение файлов — MinIO (S3).
- Сервис следует чистой архитектуре: domain → application → infrastructure → transport, зависимости только внутрь; S3 и прочие внешние системы доступны через порты, домен и application не зависят от FastAPI/адаптеров.
- Identity приходит только заголовками api-gateway (`X-User-Id`, `X-Company-Id`, `X-Role`); сервис не парсит JWT. `company_id` обязателен, фильтрация выборок — в репозитории; отсутствие identity означает отказ.
- У сервиса отдельная база в общем Postgres и собственные миграции Alembic; читать базы других сервисов напрямую запрещено.
- Наружу экспонируется только api-gateway; pdf-extract доступен лишь во внутренней сети.
- Конвейер: загрузка → извлечение текста → LLM-спецификация → маппинг → расчёт. Выбор брокера очереди отложен, поэтому контракт текстового артефакта должен быть нейтрален к транспорту.
- Конвенции: идентификаторы — UUID; время — ISO-8601 UTC; ошибки — RFC 7807 `application/problem+json`; списки — `limit`/`offset`; версия API — в пути (`/v1/...`); имена полей — `snake_case`.
- Стек: Python ≥ 3.12, FastAPI, SQLAlchemy, Alembic, MinIO; сервис размещается в `smeta/pdf-extract/`.

## UX & Interaction Patterns

- Сценарий: сметчик загружает цифровой PDF в рамках работы со сметой; при отказе показывается понятная причина (превышен размер, отсутствует текстовый слой, неподдерживаемый формат).
- Сообщения об ошибках не должны раскрывать внутренние детали хранения; успешная загрузка даёт понять, что файл принят и доступен для дальнейшей обработки.

## Cross-Story Dependencies

- Story 4.2 выполняется после Story 4.1: конвертация возможна только для валидированного файла, сохранённого в MinIO.
- Текстовый артефакт Story 4.2 — вход для LLM-извлечения спецификации в Epic 5, поэтому сохраняемая структура строк/таблиц важнее «плоского» текста.
- Загрузка требует аутентификации и контекста компании (Epic 2), а также инфраструктуры MinIO и Postgres (Epic 1).
- Отложенный выбор брокера очереди влияет на способ передачи артефакта в следующий шаг, но не на его содержимое.
