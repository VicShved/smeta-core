# Epic 2 Context: Аутентификация, компании и иерархия договоров

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Дать сметчику вход в систему с изолированным рабочим пространством своей организации и заложить доменную иерархию, на которую опираются все последующие эпики: от компании — через договоры произвольной вложенности — к этапам, подразделам этапа и сметам. Эпик вводит идентичность и арендатора (tenant) как сквозной контракт: edge-шлюз доказывает личность токеном и передаёт её заголовками, каждый сервис обязан фильтровать доменные данные по компании. Здесь фиксируются решения AD-010…AD-015, определяющие структуру кода и БД всех сервисов. Edge-контракт (AD-010) уже реализован внеплановой Story 2.0 и остаётся неизменным контекстом для остальных историй эпика.

## Stories

- Story 2.0 (внеплановая): Edge-слой api-gateway — JWT и identity-заголовки (AD-010)
- Story 2.1: Авторизация и привязка к компании
- Story 2.2: Договоры произвольной глубины (adjacency list)
- Story 2.3: Этапы договора
- Story 2.4: Подразделы этапа

## Requirements & Constraints

- Один тип пользователя (сметчик), **одна роль**. Мультикомпанийность и роли >1 — вне MVP.
- Регистрация создаёт новую компанию по умолчанию и привязывает к ней пользователя; отдельного сценария «вступить в существующую компанию» в MVP нет.
- После входа пользователь получает сессию/токен; данные компании изолированы от других компаний (изоляция проверяема, а не декларативна).
- Договоры — иерархия произвольной глубины; циклы и ссылки на несуществующие узлы запрещены валидацией; доступно получение дерева договоров компании целиком.
- Этапы привязаны к договору (несколько на договор), подразделы — к этапу (несколько на этап); этапы/подразделы доступны для привязки смет.
- Наружу публикуется только api-gateway; остальные сервисы — во внутренней сети (граница доверия).
- Целевые объёмы MVP (влияют на решения о производительности, не на функциональность): 20–50 смет/мес, 100–500 позиций/смета.
- Запуск локально через Docker Compose; конфигурация — через переменные окружения; готовность к Kubernetes.

## Technical Decisions

- **AD-010 JWT, проверка только на edge** (реализовано в Story 2.0). HS256, единый HMAC-секрет знают только `auth-users` (выпуск) и `api-gateway` (проверка). Claims: `sub`, `company_id`, `role`, `iat`, `exp`; TTL 168ч, без refresh-токенов. Внутрь identity идёт заголовками `X-User-Id`, `X-Company-Id`, `X-Role`; gateway удаляет/перезаписывает входящие заголовки с этими именами; внутренние сервисы токен не парсят. Межсервисные вызовы пробрасывают те же заголовки.
- **AD-011 Чистая архитектура.** Слои: `domain` → `application` (use cases, порты) → `infrastructure` (адаптеры: БД, HTTP) → `transport` (FastAPI). Зависимости только внутрь; `domain`/`application` не импортируют FastAPI/SQLAlchemy. Исключение — `llm-gateway` (перестроится позже).
- **AD-012 Владение user и company.** `auth-users` владеет `user` и credentials, `company-org` владеет `company`. Регистрация: auth-users создаёт user → вызывает API company-org → сохраняет `company_id`. Распределённой транзакции нет; создание компании идемпотентно; согласованность — через компенсацию при сбое. Прямой доступ к чужим сущностям в обход API запрещён.
- **AD-013 Tenancy по `company_id`.** `company_id` — на агрегатных корнях (`contract`, `estimate`, `rate_catalog`) и напрямую адресуемых дочерних строках (`stage`, `stage_subdivision`); позиции смет получают scope через владельца-версию. Доступ по id дополнительно проверяет `company_id` владельца; фильтрация — в репозитории. Без identity — отказ, а не выборка всех строк.
- **AD-014 Один Postgres, база на сервис.** Отдельная база на сервис; миграции — Alembic, у каждого сервиса свои; чужие БД только через API (межсервисных join'ов нет).
- **AD-015 Циклы и сироты в иерархии.** Валидация в application-слое `company-org`: подъём по `parent_id` до корня, отказ при цикле, самоссылке и несуществующем родителе; покрыта тестами.
- **AD-009 Поли-репо.** Каждый сервис — отдельный репозиторий `smeta/<service>/`; общий деплой — `smeta/deploy/`; shared-lib нет, контракты — только через API.
- **Data Model (ключевые сущности).** `company` (id, name); `user` (id, company_id, role, credentials) — владелец auth-users; `contract` (id, company_id, parent_id, name); `stage` (id, company_id, contract_id, name); `stage_subdivision` (id, company_id, stage_id, name).
- **Стек:** Python ≥3.12, FastAPI, Uvicorn, Pydantic 2, SQLAlchemy 2, Alembic, psycopg 3, PyJWT 2 (HS256), PostgreSQL; ui — Vue. Идентификаторы — UUID, ошибки — RFC 7807 `application/problem+json`, версионирование API — в пути (`/v1/...`), JSON/БД — `snake_case`.
- **Секреты** (в т.ч. HMAC-секрет JWT) передаются через env; управление секретами — Deferred.

## Cross-Story Dependencies

- Story 2.0 зафиксирована в эпике задним числом: контракт AD-010 уже реализован и не меняется; Story 2.1 выпускает токены, которые проверяет готовый edge-слой.
- Stories 2.2–2.4 опираются на компании и identity из Story 2.1 (нет компании — нет договоров) и на валидацию иерархии AD-015.
- Эпики 3–7 зависят от tenancy-контракта (AD-013) и identity-заголовков (AD-010): сметы, справочник и расчёт обязаны фильтровать по `company_id`.
- Эпик 1 дал инфраструктуру (compose, llm-gateway); Epic 2 вводит фактический edge-слой (api-gateway как единственная точка входа).
