# smeta1 - Requirements Breakdown

## Overview

Данный документ содержит полную декомпозицию эпиков и историй для **smeta1** — системы автоматизации обработки строительных смет в цифровых PDF. Требования декомпозированы из PRD и Architecture Spine (AD-001..AD-008) в имплементируемые истории с критериями приёмки для разработчика.

## Requirements Inventory

### Functional Requirements

- FR-001: Авторизация и привязка пользователя к компании (по умолчанию новая компания). Публичная регистрация — `estimator`; `admin` — bootstrap.
- FR-002: Иерархия Компания → Договор (произвольная глубина) → Этап → Сметы. (2026-10-20: уровни «Подраздел этапа» упразднён — сметы привязываются к этапу.)
- FR-003: Загрузка цифрового PDF в S3 (MinIO) с валидацией (только цифровой PDF, ≤ 50 МБ).
- FR-004: Конвертация PDF → текст (pdfplumber/pypdfium2), без OCR.
- FR-005: LLM-извлечение спецификации (материал/работа, ЕИ, количество, раздел). Покрытие ≥ 95%.
- FR-006: Сопоставление позиций со справочником расценок по эмбеддингам с confidence (cosine 0–1); после привязки — пересчёт ЕИ (FR-018). Поиск за точный регион/год/квартал/зону. Покрытие ≥ 90–95%.
- FR-007: Ручная проверка/исправление сопоставления: `confirm`/`correct`/`reject`/`unmatch`, выбор материала, ручной коэффициент, «нет в справочнике».
- FR-008: Импорт справочника расценок из Excel (.xlsx) с маппером колонок; региональная база 2022 и цены по кварталам/зонам.
- FR-009: Детерминированный расчёт детальной и итоговой стоимости по `qty_catalog_snapshot × rate_amount_snapshot`; LLM не участвует.
- FR-010: Версии смет: несколько версий, ровно одна активная; готовность к diff (UI — 1.1).
- FR-011: Отображение детальной и итоговой стоимости, исходной и пересчитанной ЕИ в простом UI.
- FR-012: Аудит использования облачной LLM (attempt/fallback/denied/allowed).
- FR-013: Управление LLM-провайдерами/моделями и активной моделью компании; `api_key_env` без хранения ключей; аудит изменений.
- FR-014: Статусы обработки и деградация при недоступности внешних сервисов.
- FR-015: Удаление сметы и исходного файла с каскадной очисткой.
- FR-016: Просмотр справочника цен за период/зону и управление эмбеддингами.
- FR-017: Append-only журнал `match_feedback` и JSONL-экспорт ручных решений.
- FR-018: Пересчёт ЕИ сметы в ЕИ справочника после привязки: словарь/кратность, размеры 2D/3D, упаковка, ручной коэффициент; неизвестное — `conversion_required`, позиция вне расчёта.
- FR-019: Глобальный редактируемый словарь ЕИ и правил пересчёта с аудитом; правки доступны всем авторизованным.

### NonFunctional Requirements

- NFR-001: Локальная LLM — CPU-only, 8 ГБ ОЗУ, GGUF малых квантов q2–q3, без GPU.
- NFR-002: Гибрид local+cloud: `llm.allow_cloud_fallback=false` по умолчанию; `llm.redaction_mode=structure_only`; во внешнюю LLM только структурно-анонимизированные фрагменты.
- NFR-003: Поддержка только цифровых PDF (текстовый слой); OCR вне MVP.
- NFR-004: Стек: Python, FastAPI, Vue, Postgres + pgvector, MinIO (S3).
- NFR-005: Запуск локально через Docker Compose; готовность к Kubernetes.
- NFR-006: Время обработки 30–60с при локальной CPU-only модели (100–500 позиций).
- NFR-007: Объёмы MVP: 20–50 смет/месяц, 100–500 позиций/смета, PDF ≤ 50 МБ.
- NFR-008: Доля позиций с confidence < 0.70 ≤ 15% (цель).
- NFR-009: Расчёт 100% детерминирован (проверяется тестами).
- NFR-010: Пересчёт ЕИ 100% детерминирован: `qty_catalog` — 4 знака `ROUND_HALF_UP`, `conversion_factor` — `Numeric(24,12)`, Decimal precision 28, float запрещён.
- NFR-011: Привязанная позиция с несовпадающей ЕИ имеет правило или `conversion_required`; молчаливо неверных стоимостей — 0.
- NFR-012: Словарь ЕИ глобальный, правки аудируются; рассчитанные версии заморожены снапшотами, массовый пересчёт при правке словаря не выполняется.

### Additional Requirements

- AR-001: Snapshot расценок/ЕИ в позициях сметы (`rate_snapshot_id`, `unit_snapshot`, `rate_amount_snapshot`) — изменения справочника не влияют на рассчитанные версии (AD-002).
- AR-002: Договоры — adjacency list (`parent_id`), произвольная глубина (AD-006).
- AR-003: Обработка конвейера асинхронная; очередь — таблица `spec_job` в Postgres (`FOR UPDATE SKIP LOCKED`), отдельный брокер не вводится.
- AR-004: Микросервисные границы: api-gateway, auth-users, company-org, estimate, pdf-extract, spec-service, llm-proxy, llm-gateway, rate-catalog, s3/minio, ui, deploy.
- AR-005: AD-017 — `estimate` владеет детерминированным пересчётом; `conversion_factor` направлен «ЕИ сметы → ЕИ справочника»; ручной коэффициент переопределяет правила; снапшоты `qty_catalog_snapshot`/`conversion_factor_snapshot`/`unit_snapshot`.
- AR-006: AD-018 — глобальные `unit_conversion_rule`, `unit_conversion_alias`, `unit_conversion_audit` без `company_id` (исключение AD-013); правка через API `estimate`; UI — редактор.
- AR-007: Миграция nullable; рассчитанные версии не backfill-ятся; активные нерассчитанные пересчитываются по явному действию; новая калькуляция требует `qty_catalog`/`conversion_factor`.

### Epic 9: Пересчёт ЕИ и словарь правил

**Цель:** после привязки позиции к материалу сметчик получает количество в ЕИ справочника, видит коэффициент и источник правила, может исправить коэффициент или правило в словаре, а расчёт использует уже пересчитанное количество. Неизвестные случаи явно помечаются, а рассчитанные версии не меняются.

**FRs covered:** FR-018, FR-019; поддерживает FR-006, FR-007, FR-009, FR-011.

**Пользовательский результат:** сметчик больше не считает стоимость по несовпадающим ЕИ вручную; он видит `исходное количество/ЕИ → количество/ЕИ справочника`, коэффициент и причину `conversion_required`, а также управляет глобальным словарём.

**Implementation notes:** `estimate` владеет словарём, движком и API; `rate-catalog` — источник `material.unit`/цены; UI — редактор и проекция. AD-017/AD-018, миграция nullable без backfill, рассчитанные версии заморожены. Stories 9.1–9.6.

## Epic 1: Базовая инфраструктура и безопасность LLM

Развернуть каркас микросервисов и llm-gateway с жёсткой политикой данных: локальный CPU-only рантайм (GGUF q2–q3, 8 ГБ ОЗУ), облачный fallback запрещён по умолчанию, разрешён только в режиме `structure_only` с аудитом. Обеспечить локальный запуск через Docker Compose и готовность к Kubernetes.

### Story 1.1: Каркас микросервисов и Docker Compose

As a разработчик,
I want единый каркас микросервисов, поднимаемый локально одной командой,
So that я мог разрабатывать и отлаживать сервисы независимо и согласованно.

**Acceptance Criteria:**

**Given** чистый репозиторий и установленный Docker Compose
**When** я запускаю `docker compose up`
**Then** поднимаются сервисы (api-gateway, auth-users, company-org, estimate, pdf-extract, spec-service, llm-proxy, llm-gateway, rate-catalog, ui) с healthcheck
**And** поднимаются Postgres и MinIO с персистентными томами
**And** конфигурация сервисов читается из переменных окружения

### Story 1.2: Локальный CPU-only LLM-рантайм (q2–q3, 8 ГБ ОЗУ)

As a сметчик,
I want локальную LLM, работающую без GPU на 8 ГБ ОЗУ,
So that система работала полностью локально на моём компьютере.

**Acceptance Criteria:**

**Given** машина с 8 ГБ ОЗУ и без GPU
**When** llm-gateway получает запрос на локальный инференс
**Then** используется GGUF-модель квантования q2–q3
**And** потребление памяти не превышает доступный лимит 8 ГБ ОЗУ
**And** запрос обрабатывается без обращения к GPU
**And** llm-gateway отдаёт единый интерфейс инференса вне зависимости от рантайма

### Story 1.3: Политика облачного fallback и аудит

As a владелец данных,
I want гарантию, что данные смет не утекают во внешнюю LLM без явного согласия,
So that конфиденциальность сметных данных соблюдалась.

**Acceptance Criteria:**

**Given** конфигурация по умолчанию
**When** система пытается выполнить облачный инференс
**Then** `llm.allow_cloud_fallback=false` блокирует запрос и фиксируется событие `denied`
**And** при `llm.redaction_mode=structure_only` во внешнюю LLM передаются только структурно-анонимизированные фрагменты (типы полей, схема), без наименований, количеств и ЕИ
**And** любое включение облачного fallback требует явного согласия и записывает событие аудита (timestamp, инициатор, причина, объём структурных блоков)
**And** все события (attempt/fallback/denied/allowed) сохраняются в журнале аудита

## Epic 2: Аутентификация, компании и иерархия договоров

Реализовать авторизацию с привязкой к компании (по умолчанию новая компания; `estimator` при регистрации, `admin` — bootstrap) и доменную иерархию: договоры произвольной глубины (adjacency list), этапы.

### Story 2.0 (внеплановая): Edge-слой api-gateway — JWT и identity-заголовки (AD-010)

Вынесено из Story 2.1 при её сужении (edge-контракт AD-010 не входил в ядро истории) и реализовано внеплановой build-спекой 2026-10-19. Зафиксировано здесь задним числом, чтобы edge-слой был виден в трекинге эпика.

As a сметчик,
I want обращаться к системе через единственную точку входа, которая проверяет мой токен,
So that внутренние сервисы не парсили токен и доверяли только доказанной identity.

**Acceptance Criteria:**

**Given** запрос к `/health` или `POST /v1/auth/register|login`
**When** он приходит без токена
**Then** он проксируется без проверки (публичные пути)
**And** для остальных `/v1/**` без валидного токена ответ — 401 `application/problem+json`
**And** неизвестный префикс → 404 без проверки токена
**And** из проверенных claims формируются `X-User-Id`/`X-Company-Id`/`X-Role`, клиентские одноимённые заголовки всегда удаляются
**And** `api-gateway` — единственный сервис с публикуемым app-портом (`8000:8000`)

**Артефакты:** `_bmad-output/implementation-artifacts/spec-2-gateway-jwt-i-identity-заголовки.md` (status: done), коммиты `api-gateway@26546b0`, `deploy@9bd1cec`; далее закрытие dev-дефолта `JWT_SECRET` (`deploy@1090621`).

### Story 2.1: Авторизация и привязка к компании

As a сметчик,
I want авторизоваться и автоматически привязаться к компании,
So that я работал в изолированном пространстве своей организации.

**Acceptance Criteria:**

**Given** незарегистрированный пользователь
**When** он регистрируется впервые
**Then** создаётся новая компания и пользователь привязывается к ней
**And** роль пользователя — `estimator` (публичная регистрация); `admin` создаётся bootstrap-скриптом
**And** пользователь может войти и получить сессию/токен
**And** данные компании изолированы от других компаний

### Story 2.2: Договоры произвольной глубины (adjacency list)

As a сметчик,
I want создавать договоры с произвольной вложенностью,
So that отразить реальную структуру сотрудничества/подряда.

**Acceptance Criteria:**

**Given** авторизованный пользователь со своей компанией
**When** он создаёт договор с указанием `parent_id`
**Then** договор встраивается в иерархию на произвольную глубину

### Story 2.3: Этапы договора

As a сметчик,
I want привязывать этапы к договору,
So that сметы группировались по этапам работ.

**Acceptance Criteria:**

**Given** существующий договор
**When** пользователь создаёт этап
**Then** этап привязан к договору
**And** у одного договора может быть несколько этапов
**And** этапы доступны для последующей привязки смет

## Epic 3: Справочник расценок

Реализовать ведение справочника расценок: импорт только из Excel (.xlsx) с маппером колонок и версионированием. Позиции смет ссылаются на snapshot расценок/ЕИ, поэтому изменения справочника не меняют уже рассчитанные версии смет.

### Story 3.1: Импорт справочника из Excel с маппером колонок

As a сметчик,
I want импортировать справочник расценок из Excel,
So that система использовала актуальные расценки для расчёта.

**Acceptance Criteria:**

**Given** файл `.xlsx` со справочником расценок
**When** пользователь загружает файл
**Then** система предлагает сопоставить колонки (наименование, ЕИ, цена/расценка и др.) через маппер
**And** импортируются только распознанные строки; некорректные строки помечаются с причиной
**And** форматы кроме `.xlsx` отклоняются

### Story 3.2: Версионирование справочника (не реализовано, заменено 3.5)

> **As-built 2026-10-25:** таблиц `rate_catalog`/`rate_catalog_version` нет; справочник глобальный и региональный, импорт обновляет строки по естественному ключу. Замена — Story 3.5.

As a сметчик,
I want видеть версии справочника,
So that понимать, на какой версии основан расчёт сметы.

**Acceptance Criteria:**

**Given** успешно импортированный справочник
**When** импорт завершается
**Then** создаётся `rate_catalog_version` (version, imported_at, source_file_hash, created_by)
**And** каждому пользователю/компании доступен единый справочник с историей версий
**And** можно получить текущую активную версию справочника

### Story 3.3: Snapshot расценок в позициях смет

As a сметчик,
I want, чтобы изменения справочника не искажали уже рассчитанные сметы,
So that результаты прошлых расчётов оставались воспроизводимыми.

**Acceptance Criteria:**

**Given** рассчитанная версия сметы с позициями
**When** импортируется новая версия справочника
**Then** позиции сохраняют `rate_snapshot_id`, `unit_snapshot`, `rate_amount_snapshot` на момент расчёта
**And** активная версия сметы и её стоимость не меняются
**And** рассчитанная версия замораживается: повторный расчёт запрещён, новая редакция оформляется новой версией сметы

## Epic 4: Загрузка и извлечение цифрового PDF

Реализовать загрузку цифрового PDF-сметы в MinIO с валидацией и конвертацию PDF → текст без OCR. Поддерживаются цифровые PDF (ГРАНД-Смета, АВК-Смета, совместимые).

### Story 4.1: Загрузка цифрового PDF в MinIO с валидацией

As a сметчик,
I want загружать PDF-смету,
So that система могла извлечь из неё спецификацию.

**Acceptance Criteria:**

**Given** авторизованный пользователь
**When** он загружает PDF-файл
**Then** файл сохраняется в MinIO (S3), создаётся запись `file` (storage_key, mime_type, size, meta)
**And** файлы > 50 МБ отклоняются с понятной ошибкой
**And** файлы без текстового слоя (сканы) отклоняются как неподдерживаемые (OCR вне MVP)

### Story 4.2: Конвертация PDF → текст (без OCR)

As a сметчик,
I want получать текстовое представление загруженной сметы,
So that LLM могла извлечь из него спецификацию.

**Acceptance Criteria:**

**Given** загруженный цифровой PDF с текстовым слоем
**When** срабатывает pdf-extract
**Then** извлекается текст с сохранением структуры строк/таблиц (pdfplumber/pypdfium2)
**And** результат сохраняется и передаётся в конвейер как артефакт
**And** покрытие извлечения для типовых PDF ГРАНД-Смета/АВК-Смета ≥ 95% (проверка на тестовом наборе)

## Epic 5: Извлечение спецификации и маппинг с confidence

Реализовать LLM-извлечение спецификации (материал/работа, ЕИ, количество, раздел) через local-first llm-gateway, сопоставление со справочником расценок с confidence и нормализацией ЕИ, а также API ручной проверки. Полный UI валидации — 1.1.

### Story 5.1: LLM-извлечение спецификации (local-first)

As a сметчик,
I want автоматически получать спецификацию из текста сметы,
So that не переносить позиции вручную.

**Acceptance Criteria:**

**Given** текстовый артефакт извлечённой сметы
**When** вызывается llm-spec через llm-gateway
**Then** формируется список позиций: материал/работа, ЕИ, количество, раздел сметы

## Epic 9: Пересчёт ЕИ и словарь правил

**Цель:** после привязки позиции к материалу сметчик получает количество в ЕИ справочника, видит коэффициент и источник правила, может исправить коэффициент или правило в словаре, а расчёт использует пересчитанное количество. Неизвестные случаи явно помечаются, рассчитанные версии не меняются.

**FRs covered:** FR-018, FR-019; поддерживает FR-006, FR-007, FR-009, FR-011.

### Story 9.1: Модель словаря, миграция и детерминированный движок

As a сметчик,
I want чтобы система хранила правила и сразу пересчитывала количество в ЕИ справочника,
So that я видел корректную единицу и мог проверить, откуда взялся коэффициент.

**Acceptance Criteria:**

**Given** пустая или уже существующая БД `estimate`
**When** применяются миграции Epic 9
**Then** созданы глобальные таблицы `unit_conversion_rule`, `unit_conversion_alias`, `unit_conversion_audit` без `company_id`
**And** `unit_conversion_rule` хранит `kind` (`alias|multiple|dimensions|package`), `dimension` (`length|area|volume|mass|count`), `base_unit` из `m|m2|m3|kg|шт`, `factor_to_base?`, `multiple?`, `config?`, целочисленный `priority`, `enabled`, автора и timestamps
**And** `unit_conversion_alias` хранит нормализованный уникальный alias и ссылку на правило; рёбер alias→alias нет
**And** `estimate_item` получает nullable-поля `qty_catalog`, `unit_catalog`, `conversion_factor Numeric(24,12)`, `conversion_source`, `conversion_required` (default false), `conversion_reviewed_at/by`, `conversion_note`, `qty_catalog_snapshot`, `conversion_factor_snapshot`
**And** существующие колонки и рассчитанные версии не меняются; backfill не выполняется
**And** миграции проходят на пустой и существующей БД; активные нерассчитанные позиции читаются с пустыми полями пересчёта

**Given** позиция с `qty`, `unit_orig`, `name` и привязанным материалом с `material.unit`
**When** выполняется пересчёт
**Then** `qty_catalog = qty × conversion_factor`, а `qty`/`unit_orig` не меняются
**And** ручной `conversion_factor` (`conversion_source=manual`) всегда переопределяет словарь и правила
**And** иначе приоритет: точное/нормализованное совпадение ЕИ → словарь/кратность → размеры → упаковка
**And** `unit_orig` — единица количества (`шт`, `м`, `м²`, `кг`), а не размер материала; размеры материала разбираются из `name`, а `unit_orig` используется как fallback только при отсутствии размеров; поддерживаются `x/х/×/*`, 2–3 измерения, явные `mm/cm/m`, без единицы — мм
**And** `unit_orig=шт`, `name=Плитка 200х300 мм`, `qty=2` при ЕИ `м²` даёт `qty_catalog=0.1200`; `unit_orig=шт`, `name=200х300х4000 мм`, `qty=2` при ЕИ `м³` — `0.4800`
**And** формула зависит от измерения `unit_orig`: `шт/упак → м²/м³` — площадь/объём изделия × количество; `м → м²` — периметр сечения × количество; `м → м³` — объём по сечению (площадь сечения × количество); объём материала со стенкой требует толщины, иначе `conversion_required`; `м²/м³` — identity; `кг/т` — словарь/упаковка; иначе `conversion_required`
**And** воздуховод: `unit_orig=м`, `name=200х300 мм`, `qty=5`, ЕИ `м²` → `(0.2 + 0.3) × 2 × 5 = 5.0000`; для `м³` — `0.2 × 0.3 × 5 = 0.3000`
**And** `упак 25 кг` → `кг` даёт коэффициент `25`; `100 шт` в ЕИ → `шт` — `100`; обратное направление делит
**And** обратный пересчёт `м²/м³ → шт/упак` допустим только при положительной площади/объёме изделия
**And** конфликт — только если `unit_orig` содержит размеры и они расходятся с `name`; тогда `conversion_required`, а не молчаливый выбор
**And** `qty_catalog` квантуется до 4 знаков `ROUND_HALF_UP`, `conversion_factor` — до 12, Decimal precision 28, float запрещён
**And** неизвестное правило выставляет `conversion_required=true` и не заполняет `qty_catalog`
**And** пересчёт идемпотентен: повторный вызов с теми же входом и правилом даёт тот же результат; LLM и сеть не используются
**And** покрыты случаи: нулевые/отрицательные размеры, конфликт двух источников размеров, несколько подходящих правил, отсутствие правила

### Story 9.6: Доказательство — детерминизм, e2e и защита от молчаливых ошибок

As a команда,
I want доказательство, что пересчёт детерминирован и не даёт молчаливо неверных стоимостей,
So that выпускать изменение без риска для расчётов.

**Given** реальный Postgres и тестовые данные Epic 9
