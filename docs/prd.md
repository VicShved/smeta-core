# PRD: smeta1

## 1. Overview

smeta1 — система для автоматизации обработки смет в цифровых PDF. Сметчик загружает цифровой PDF-смету, система извлекает спецификацию (материал/работа, ЕИ, количество, раздел), сопоставляет с справочником расценок, нормализует ЕИ и рассчитывает детальную/итоговую стоимость.

Ключевые принципы: микросервисная архитектура, локальная LLM CPU-only (16 ГБ ОЗУ), гибрид local+cloud с жёсткой политикой редактирования данных, детерминированный расчёт, версионирование смет со snapshot-расценок, произвольная иерархия договоров.

## 2. Problem Statement

Сметчик вручную переносит позиции из цифровых PDF в рабочие инструменты: извлекает спецификацию, приводит ЕИ к справочной, ищет расценку, считает стоимость. Отсутствует версионирование при изменениях сметы, нет единого представления иерархии «Договор → Этап → Смета», сложно сравнить версии.

## 3. Goals (MVP)

- Автоматизировать конвейер PDF→спецификация→маппинг→расчёт.
- Сопоставление с confidence + ручная проверка (UI 1.1).
- Единый справочник расценок (импорт из Excel) с версионированием и snapshot-ссылками на позиции сметы.
- Произвольная иерархия: Компания → Договор (произв. глубина) → Этап → Сметы (по подразделам этапа).
- Версии смет: несколько, ровно одна активная; заложить возможность diff (UI 1.1).
- Безопасный гибрид LLM: по умолчанию запрет облачного fallback с данными сметы.

## 4. Closed Open Questions

### Q1. Облачная LLM и данные (РЕШЕНО)
- По умолчанию `llm.allow_cloud_fallback = false`.
- `llm.redaction_mode = structure_only`. Во внешнюю LLM **не передавать** наименования, количества, ЕИ, номера позиций, названия файлов, прочие ПДн из сметы.
- Допустимы только структурно-анонимизированные фрагменты: типы полей, схема таблицы, признаки формата, статистика токенов, без значений.
- Включение облачного fallback требует **явного согласия** оператора/пользователя и фиксируется в **аудите** (timestamp, инициатор, причина, объём отправленных структурных блоков).
- Запретить «mixed mode»: при `structure_only` никакие текстовые фрагменты исходной спецификации не уходят наружу.

### Q2. Источники PDF
- Целевые форматы: цифровые PDF, созданные **ГРАНД-Смета**, **АВК-Смета** (и совместимые по текстовому слою).
- Поддержка только цифровых PDF (текстовый слой). OCR **не** планируется в MVP.
- Цель покрытия извлечения спецификации: **≥ 95%** на типовых цифровых PDF указанных источников.

### Q3. Объёмы (MVP)
- 20–50 смет/месяц
- 100–500 позиций/смета
- Размер PDF ≤ 5 МБ

### Q4. Справочник расценок
- Единый на компанию.
- Версионирование: `rate_catalog(id, version, imported_at, source_file_hash, created_by)`.
- При импорте из Excel (.xlsx) используется **маппер колонок** (наименование, ЕИ, цена/расценка, прочие при наличии).
- **Snapshot-подход**: при расчёте сметы позиции сохраняют ссылку на snapshot расценки/ЕИ (`estimate_item.rate_snapshot_id`, `estimate_item.unit_snapshot`, `estimate_item.rate_amount_snapshot`) на момент расчёта. Изменение текущей версии справочника **не влияет** на уже рассчитанные активные версии смет.

### Q5. «Подраздел этапа»
- «Подраздел этапа» (subdivision_of_stage) — подпункт/раздел внутри этапа договора. Сметы привязываются к этапу с группировкой по этому подразделу.

### Q6. Порог confidence 0.70
- Целевой порог **0.70** для предложений маппинга.
- Позиции с `confidence < 0.70` помечаются как требующие проверки.
- Цель: доля таких позиций **≤ 15%**.
- Калибровка порога по реальным PDF — **после MVP** (не блокер релиза).

## 5. Functional Requirements (ключевые, с ID)
- FR-001: Авторизация + привязка к компании (по умолчанию новая). Одна роль.
- FR-002: Иерархия Компания→Договор (произвольная глубина)→Этап→Сметы (по подразделам этапа).
- FR-003: Загрузка цифрового PDF в S3 (MinIO). Валидация: только цифровой PDF, размер ≤ 5 МБ.
- FR-004: PDF→текст (pdfplumber/pypdfium2). Без OCR.
- FR-005: LLM-извлечение спецификации (материал/работа, ЕИ, количество, раздел). Цель покрытия ≥95%.
- FR-006: Маппинг со справочником с confidence (0–1). Нормализация ЕИ.
- FR-007: Ручная проверка маппинга пользователем (UI валидации — 1.1). API для подтверждения/исправления готово в MVP.
- FR-008: Импорт справочника из Excel (.xlsx) с маппером колонок. Версионирование + snapshot.
- FR-009: Расчёт детальной и итоговой стоимости. **Только детерминированный** (формулы). LLM не выполняет арифметику.
- FR-010: Версии смет: несколько версий, ровно одна активная. Архитектура поддерживает diff (UI — 1.1).
- FR-011: Отображение детальной/итоговой стоимости в простом UI.
- FR-012: Аудит облачного LLM при использовании (события: attempt/fallback/denied/allowed).

## 6. Non-Functional Requirements
- Архитектура: микросервисы (UI Vue, Auth+Users, S3/MinIO, pdf-extract, llm-spec, llm-mapping, rate-catalog, calc, gateway).
- LLM: **гибрид local+cloud**. Локальная модель — **CPU-only**, 16 ГБ ОЗУ, GGUF малых квантов (**q2–q3**). Без GPU.
- Стек: Python, FastAPI, Vue, Postgres, MinIO (S3).
- Деплой: локально Docker Compose, готовность к Kubernetes.
- Безопасность данных: redaction_mode=structure_only при cloud fallback, флаг allow_cloud_fallback=false по умолчанию, аудит.
- Производительность: 30–60с при локальной CPU-only модели (типовой PDF 100–500 позиций).
- Качество: spec coverage ≥95%, price mapping ≥90–95%, confidence<0.70 ≤15%.
- Корректность расчёта: 100% детерминирована.

## 7. Success Metrics
- Spec extraction coverage (цифровые PDF) ≥ 95%
- Price mapping success rate ≥ 90–95%
- Доля позиций с confidence < 0.70 ≤ 15%
- Время обработки при локальной CPU-only ≤ 30–60с
- Арифметика детерминирована: 100% (контроль тестами)

## 8. Risks
- Локальная CPU-only модель на 16ГБ RAM — приоритет q2–q3, гибридный fallback при соблюдении политики.
- Разнообразие Excel-структур — маппер колонок.
- Качество маппинга — confidence + ручная проверка (UI 1.1).
- Разная вёрстка PDF ГРАНД/АВК — покрытие метрикой ≥95%.

## 9. Assumptions
- Только цифровые PDF с текстовым слоем.
- Импорт справочника только из Excel (.xlsx).
- Одна роль, один тип пользователя (сметчик).
- Snapshot расценок решает версионность справочника относительно смет.
