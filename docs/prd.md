# PRD: smeta1

> Полная актуальная версия PRD: `_bmad-output/planning-artifacts/prds/prd-core-2026-10-25/prd.md` (BMAD-формат, Story 8.2 включена). Этот файл — краткая проектная справка.

## 1. Overview

smeta1 — система для автоматизации обработки смет в цифровых PDF. Сметчик загружает цифровой PDF-смету, система извлекает спецификацию (материал/работа, ЕИ, количество, раздел), сопоставляет с справочником расценок, нормализует ЕИ и рассчитывает детальную/итоговую стоимость.

Ключевые принципы: микросервисная архитектура, локальная LLM CPU-only (8 ГБ ОЗУ), гибрид local+cloud с жёсткой политикой редактирования данных, детерминированный расчёт, версионирование смет со snapshot-расценок, произвольная иерархия договоров.

## 2. Problem Statement

Сметчик вручную переносит позиции из цифровых PDF в рабочие инструменты: извлекает спецификацию, приводит ЕИ к справочной, ищет расценку, считает стоимость. Отсутствует версионирование при изменениях сметы, нет единого представления иерархии «Договор → Этап → Смета», сложно сравнить версии.

## 3. Goals (MVP)

- Автоматизировать конвейер PDF→спецификация→маппинг→расчёт.
- Сопоставление с confidence + ручная проверка (UI 1.1).
- Единый справочник расценок (импорт из Excel) с версионированием и snapshot-ссылками на позиции сметы.
- Произвольная иерархия: Компания → Договор (произв. глубина) → Этап → Сметы. (2026-10-20: уровень «Подраздел этапа» упразднён — см. Q5.)
- Версии смет: несколько, ровно одна активная; заложить возможность diff (UI 1.1).
- Безопасный гибрид LLM: по умолчанию запрет облачного fallback с данными сметы.

## 4. Closed Open Questions

### Q1. Облачная LLM и данные (РЕШЕНО)
- По умолчанию `llm.allow_cloud_fallback = false`.
- `llm.redaction_mode = structure_only`. Во внешнюю LLM **не передавать** наименования, количества, ЕИ, номера позиций, названия файлов, прочие ПДн из сметы.
- Допустимы только структурно-анонимизированные фрагменты: типы полей, схема таблицы, признаки формата, статистика токенов, без значений.
- Включение облачного fallback требует **явного согласия** оператора/пользователя и фиксируется в **аудите** (timestamp, инициатор, причина, объём отправленных структурных блоков).
- Запретить «mixed mode»: при `structure_only` никакие текстовые фрагменты исходной спецификации не уходят наружу.

### Q2. Источники PDF
- Целевые форматы: цифровые PDF, созданные **ГРАНД-Смета**, **АВК-Смета** (и совместимые по текстовому слою).
- Поддержка только цифровых PDF (текстовый слой). OCR **не** планируется в MVP.
- Цель покрытия извлечения спецификации: **≥ 95%** на типовых цифровых PDF указанных источников.

### Q3. Объёмы (MVP)
- 20–50 смет/месяц
- 100–500 позиций/смета
- Размер PDF ≤ 50 МБ

### Q4. Справочник расценок
- **Решено 2026-10-24:** справочник **глобальный** (общий для всех компаний), без `company_id`. Материал уникален в пределах региона (`region_code`, `code`).
- База 2022 хранится отдельно (`material_base_price`, 1:1 к материалу); текущие цены/индексы — `material_price` по году, кварталу и ценовой зоне.
- При импорте из Excel (.xlsx) используется **маппер колонок** (наименование, ЕИ, цена/расценка, прочие при наличии). Поддерживаются старый формат КСР и сплит-форма ФСБЦ.
- Версий справочника нет: повторный импорт обновляет строки по естественному ключу. Отдельная `rate_catalog_version` не создаётся.
- **Snapshot-подход**: при расчёте сметы позиции сохраняют ссылку на snapshot расценки/ЕИ (`estimate_item.rate_snapshot_id`, `estimate_item.unit_snapshot`, `estimate_item.rate_amount_snapshot`) на момент расчёта. Изменение справочника **не влияет** на уже рассчитанные активные версии смет.

### Q5. «Подраздел этапа»
- **Решено 2026-10-20:** сущность «Подраздел этапа» (subdivision_of_stage) **упразднена**. Сметы привязываются напрямую к этапу (`estimate.stage_id`); группировка работ по подразделам отложена до появления реальной потребности.
- Ранее предлагалось: подпункт/раздел внутри этапа договора, к которому группируются сметы. Проверено в ходе Epic 2 и снято владельцем продукта (Story 2.4 отменена, код откатан).

### Q6. Порог confidence 0.70
- Целевой порог **0.70** для предложений маппинга.
- Позиции с `confidence < 0.70` помечаются как требующие проверки.
- Цель: доля таких позиций **≤ 15%**.
- Калибровка порога по реальным PDF — **после MVP** (не блокер релиза).

### Q7. Сопоставление позиций со справочником (Story 8.1)
- **Решено 2026-10-24:** сопоставление выполняется по эмбеддингам наименований (E5-small, pgvector, cosine), а не LLM.
- Период справочника (регион/год/квартал/зона) хранится в смете; поиск идёт только среди цен за точный период и зону.
- `confidence` — cosine score в диапазоне 0..1 (4 знака); `needs_review` — порог 0.70. Автоматическое подтверждение не выполняется: статус остаётся `proposed`.
- Повторное сопоставление обновляет только `proposed`; `confirmed`/`corrected` не перезаписываются.

### Q8. Ценовые зоны
- **Решено 2026-10-25:** регион, год, квартал и зона задаются при импорте справочника и в периоде сметы; отдельного справочника зон пока нет.
- Цена для смет — `base_estimate_price × index_value` с fallback на текущую цену; зона участвует в ключе `material_price`.

## 5. Functional Requirements (ключевые, с ID)
- FR-001: Авторизация + привязка к компании (по умолчанию новая). Публичная регистрация — роль `estimator`; `admin` создаётся bootstrap-скриптом.
- FR-002: Иерархия Компания→Договор (произвольная глубина)→Этап→Сметы.
- FR-003: Загрузка цифрового PDF в S3 (MinIO). Валидация: только цифровой PDF, размер ≤ 50 МБ.
- FR-004: PDF→текст (pdfplumber/pypdfium2). Без OCR.
- FR-005: LLM-извлечение спецификации (материал/работа, ЕИ, количество, раздел). Цель покрытия ≥95%.
- FR-006: Сопоставление позиций со справочником по эмбеддингам с confidence (cosine 0–1), нормализация ЕИ. Поиск — за точный регион/год/квартал/зону.
- FR-007: Ручная проверка маппинга: UI `reject`/`correct` по ссылке/коду, API `confirm`; каждое действие пишется в append-only `match_feedback`. Полный UI валидации — 1.1.
- FR-008: Импорт справочника из Excel (.xlsx) с маппером колонок; региональная база 2022 и цены по кварталам/зонам; snapshot в позициях смет.
- FR-009: Расчёт детальной и итоговой стоимости. **Только детерминированный** (формулы). LLM не выполняет арифметику.
- FR-010: Версии смет: несколько версий, ровно одна активная. Архитектура поддерживает diff (UI — 1.1).
- FR-011: Отображение детальной/итоговой стоимости в простом UI.
- FR-012: Аудит облачного LLM при использовании (события: attempt/fallback/denied/allowed).
- FR-013: Управление LLM-провайдерами и моделями: глобальный каталог, активная модель компании, `api_key_env` без хранения ключей, аудит изменений.
- FR-017: Журнал ручных решений `match_feedback` (confirm/correct/reject) и JSONL-экспорт для анализа/будущего обучения.

## 6. Non-Functional Requirements
- Архитектура: микросервисы (UI Vue, auth-users, company-org, S3/MinIO, pdf-extract, spec-service, llm-proxy, llm-gateway, rate-catalog, estimate, api-gateway).
- LLM: **гибрид local+cloud**. Локальная модель — **CPU-only**, 8 ГБ ОЗУ, GGUF малых квантов (**q2–q3**). Без GPU.
- Стек: Python, FastAPI, Vue, Postgres + pgvector, MinIO (S3).
- Деплой: локально Docker Compose, готовность к Kubernetes.
- Безопасность данных: redaction_mode=structure_only при cloud fallback, флаг allow_cloud_fallback=false по умолчанию, аудит.
- Производительность: 30–60с при локальной CPU-only модели (типовой PDF 100–500 позиций).
- Качество: spec coverage ≥95%, price mapping ≥90–95%, confidence<0.70 ≤15%.
- Корректность расчёта: 100% детерминирована.

## 7. Success Metrics
- Spec extraction coverage (цифровые PDF) ≥ 95%
- Price mapping success rate ≥ 90–95%
- Доля позиций с confidence < 0.70 ≤ 15%
- Время обработки при локальной CPU-only ≤ 30–60с
- Арифметика детерминирована: 100% (контроль тестами)

## 8. Risks
- Локальная CPU-only модель на 8 ГБ ОЗУ — приоритет q2–q3, гибридный fallback при соблюдении политики.
- Разнообразие Excel-структур — маппер колонок и два поддерживаемых формата (КСР, сплит-форма ФСБЦ).
- Качество сопоставления — confidence + ручная проверка (UI 1.1); порог 0.70 не откалиброван на реальном корпусе.
- Разная вёрстка PDF ГРАНД/АВК — покрытие метрикой ≥95%.

## 9. Assumptions
- Только цифровые PDF с текстовым слоем.
- Импорт справочника только из Excel (.xlsx).
- Один тип пользователя (сметчик); роли `estimator` и `admin` (bootstrap), переключателя ролей в UI нет.
- Snapshot расценок защищает рассчитанные версии смет от изменений справочника.
- Очередь конвейера — таблица `spec_job` в Postgres, отдельный брокер не вводится.
- Модель эмбеддингов — `intfloat/multilingual-e5-small` (384), CPU.
- `match_feedback` — append-only; повторное действие добавляет событие. Обучение модели автоматически не запускается.
- Текущий matching возвращает top-1 без abstention; неверные пары исправляются вручную (Story 8.2).
