# Product Brief: smeta1

## Overview

smeta1 — веб-сервис автоматической обработки смет в цифровом PDF. Сметчик загружает PDF-смету, система извлекает спецификацию (материал/работа, ЕИ, количество, раздел), сопоставляет позиции со справочником расценок по эмбеддингам, нормализует единицы измерения и рассчитывает детальную и итоговую стоимость. LLM берёт на себя извлечение, арифметика расчёта — всегда детерминированная.

Продукт закрывает узкое, но болезненное место: ручной перенос позиций из цифровых PDF-смет в рабочие инструменты сметчика — долго, ошибочно (особенно на нормализации ЕИ) и не-versionable. Один тип пользователя (сметчик); публичная регистрация даёт роль `estimator`, `admin` создаётся bootstrap-скриптом для импорта справочника.

Локальная LLM обязана работать CPU-only на машине с 8 ГБ ОЗУ; облачная LLM — гибридный fallback. Запуск локально через Docker Compose, целевой деплой — Kubernetes.

## Problem Statement

Сметчик получает сметы в виде цифровых PDF (с текстовым слоем, без сканов). Чтобы работать с ними дальше — проверить стоимость, свести с договором, сравнить редакции — позиции приходится переносить вручную: извлечь спецификацию, определить тип позиции (материал/работа), привести ЕИ к справочной, найти расценку, посчитать. Каждый шаг — источник ошибок и потерь времени.

Сегодняшний статус-кво: ручной перенос в Excel/сметные программы. Цена — часы рутины на каждую смету, ошибки нормализации ЕИ (шт/кг/м² и т.п.), отсутствие версионирования при обновлениях сметы от заказчика, невозможность быстро увидеть, что изменилось между редакциями.

Смета приходит не сама по себе: она привязана к этапу работ, этап — к договору, договор может быть иерархически вложен. Сегодня эта структура живёт в голове сметчика и файловой системе.

## Target Users

Единственный тип пользователя — **сметчик**.

- Авторизуется в системе; при регистрации привязывается к компании (по умолчанию создаётся новая компания).
- Работает с цифровыми PDF-сметами: загружает, проверяет извлечённую спецификацию, сопоставления со справочником, смотрит стоимость.
- Ожидает: система предложила сопоставления с уверенностью (confidence), низкоуверенные позиции помечены — он их проверяет и правит вручную.
- Успех для него: смета посчитана за минуты, а не часы; цифры проверяемы; ошибки видны до расчёта.

[ASSUMPTION] Одна компания на пользователя; роли `estimator`/`admin` — переключателя ролей и мультикомпанийности в UI нет.

## Goals

1. Полный конвьюер «PDF-смета → спецификация → маппинг расценок → стоимость» без ручного переноса позиций.
2. Нормализация ЕИ к справочнику расценок с предложением сопоставлений и confidence; низкоуверенные позиции (< 0.70) помечаются, доля таких позиций ≤ 15%.
3. Иерархическая структура работы: Компания → Договор (произвольная глубина) → Этап → Сметы.
4. Версионирование смет: несколько версий, ровно одна активная; архитектура данных готова к UI diff (реализация UI — 1.1).
5. Справочник расценок импортируется из Excel (.xlsx) с маппингом колонок.
6. Арифметика расчёта — 100% детерминирована, LLM в вычислениях не участвует.
7. Локальная LLM — CPU-only, 8 ГБ ОЗУ; гибридный fallback в облачную LLM.

## MVP Scope

**Включено:**
- Авторизация + привязка к компании (по умолчанию новая компания); `estimator` при регистрации, `admin` — bootstrap.
- Иерархия: договоры произвольной глубины, этапы, сметы по этапам.
- Загрузка цифрового PDF; конвертация PDF → текст; LLM-извлечение спецификации (материал/работа, ЕИ, количество, раздел).
- Сопоставление по справочнику расценок по эмбеддингам с confidence; нормализация ЕИ; ручная проверка сопоставлений через API (полноценный UI валидации — версия 1.1).
- Импорт справочника расценок из Excel (.xlsx); региональная база 2022 и цены по кварталам/зонам.
- Настройки LLM: каталог провайдеров/моделей и активная модель компании (страница `/settings/llm`).
- Детальный и итоговый расчёт стоимости, простой UI отображения.
- Версии смет: хранение нескольких версий, ровно одна активная (потенциал для diff заложен).
- Микросервисная архитектура, Docker Compose локально, подготовка к Kubernetes.

**Out of Scope (MVP):**
- OCR (только цифровые PDF с текстовым слоем).
- Экспорт в сметные форматы (XML, XLS и т.п.).
- Согласования и workflow.
- Роли > 1, мультикомпанийность.
- Расширенная аналитика и отчёты.
- UI валидации маппинга (версия 1.1).
- UI diff между версиями (версия 1.1).

## Architecture

Микросервисная архитектура. Стек: **Python, FastAPI, Vue, PostgreSQL + pgvector, MinIO (S3)**. Локальный запуск — Docker Compose; целевой деплой — Kubernetes (каркас `deploy/k8s`, пока не реализован).

**Сервисы:**
- **ui** — Vue SPA: вход, дерево, загрузка PDF, стадии обработки, экран сметы, справочник цен, импорт справочника, настройки LLM.
- **api-gateway** — единственная точка входа: проверка JWT и identity-заголовки.
- **auth-users** — авторизация, пользователи, привязка к компаниям; роли `estimator`/`admin`.
- **company-org** — компании, договоры (adjacency list) и этапы.
- **estimate** — сметы, версии, позиции, период справочника, `match-rates`, детерминированный расчёт.
- **pdf-extract** — приём PDF, хранение в MinIO, конвертация цифрового PDF в текст (без OCR).
- **spec-service** — асинхронное извлечение спецификации по `file_id`, каталог LLM-провайдеров/моделей и активная модель компании, артефакты в MinIO.
- **llm-proxy** — OpenAI-совместимый роутер alias → локальный/облачный backend, fallback и аудит.
- **llm-gateway** — локальная CPU-only LLM (GGUF q2–q3) с OpenAI API.
- **rate-catalog** — глобальный справочник регионов/материалов/цен, импорт Excel, pgvector-эмбеддинги.

**Ключевые решения:**
- LLM участвует только в извлечении спецификации; **не участвует в вычислениях** — расчёт детерминирован.
- PDF-конвейер асинхронный: загрузка → извлечение текста → LLM-спецификация → сохранение в смету → сопоставление по эмбеддингам → расчёт. Очередь — таблица `spec_job` в Postgres, отдельный брокер не вводится.
- Confidence и результат ручной проверки хранятся на позиции; порог внимания — 0.70.
- Справочник цен глобальный и региональный; период (регион/год/квартал/зона) хранится в смете.

## Data Model

- **Company** — у пользователя одна компания (при регистрации создаётся по умолчанию).
- **Contract** — договор с `parent_id` (self-reference): **произвольная иерархическая глубина**. Корневые договоры принадлежат компании.
- **Stage** — этап, принадлежит договору.
- **Estimate** — смета, привязана к этапу; несколько смет на этап. Хранит исходный файл (`source_file_id`) и период справочника (`catalog_region_code`, `catalog_year`, `catalog_quarter`, `catalog_zone`).
- **EstimateVersion** — версия сметы; **ровно одна активная** на смету. Каждая версия — полный снапшот позиций (не дельта) — это даёт **diff-потенциал**: сравнение любых двух версий без дополнительной инфраструктуры (UI diff — 1.1).
- **EstimateItem** (внутри версии) — позиция: наименование, производитель, ЕИ исходная, ЕИ нормализованная, количество, раздел, `rate_catalog_id`, `rate_code`, снапшоты, confidence, статус проверки (proposed/confirmed/corrected), стоимость.
- **Region / Material / MaterialBasePrice / MaterialPrice** — региональный справочник: материал уникален в пределах региона, база 2022 и текущие цены по кварталам/зонам.
- **MaterialEmbedding / EmbeddingJob** — векторы наименований (E5-small, 384) и фоновая задача их расчёта.
- **SpecJob** — очередь и прогресс извлечения спецификации.
- **LlmProvider / LlmModel / CompanyLlmSetting / LlmConfigAudit** — каталог провайдеров и моделей, активная модель компании и аудит изменений.

Произвольная глубина договоров, снапшотное версионирование позиций и хранение confidence на позиции — три опоры, на которых держатся иерархия, diff и качество сопоставления.

## User Flow

1. **Вход/регистрация** → создаётся/привязывается компания (по умолчанию новая).
2. **Структура**: сметчик создаёт договор (при необходимости вкладывает другой договор внутрь — произвольная глубина), внутри — этапы.
3. **Загрузка**: на этапе создаётся смета, загружается цифровой PDF.
4. **Конвьюер**: PDF → текст → LLM извлекает спецификацию → пользователь сохраняет её в активную версию сметы.
5. **Сопоставление**: `estimate` отправляет наименования позиций в `rate-catalog`, который по эмбеддингам выбирает ближайшую цену за выбранные регион/год/квартал/зону; каждой позиции присваивается confidence.
6. **Проверка**: сметчик видит детальную спецификацию; позиции с confidence < 0.70 помечены — проверяет/правит. UI валидации маппинга — 1.1; API подтверждения/исправления уже есть.
7. **Расчёт**: детальная стоимость по позициям, итог по смете.
8. **Итерация**: при обновлении PDF от заказчика загружается новая версия сметы (активной становится новая). Сравнение версий — потенциал заложен (снапшоты), UI diff — 1.1.

## Risks

1. **Локальная CPU-only LLM на 8 ГБ ОЗУ** — жёсткое ограничение. Митигация: приоритет малых GGUF (q2–q3), гибридный облачный fallback, лимиты токенов и таймауты; деградация без GPU закладывается в llm-gateway.
2. **Разнообразие структур Excel при импорте справочника** — колонки и форматы различаются. Митигация: маппер колонок, поддержка КСР и сплит-формы ФСБЦ, отчёт `rejected` по строкам.
3. **Качество сопоставления** — эмбеддинги могут выбрать нерелевантную цену. Митигация: cosine confidence, пометка низкоуверенных позиций (≤ 15% — цель), ручная проверка (полноценный UI — 1.1); калибровка порога — на реальном корпусе.
4. **Конвертация PDF** — цифровые PDF бывают «злыми» (сложная вёрстка, таблицы-картинки с текстовым слоем). Митигация: метрика coverage ≥ 95% на типичных выгрузках из сметных программ; послойное восстановление CID и лимиты разбора.

## Assumptions

- Формат входа — только цифровые PDF с текстовым слоем; сканы (OCR) не поддерживаются.
- Справочник расценок — только импорт из Excel (.xlsx).
- Один тип пользователя; роли `estimator`/`admin`; мультикомпанийность вне MVP.
- Пользователь русскоязычный; ЕИ и расценки — в парадигме ФЕР/ГЭСН-подобных справочников. [ASSUMPTION]
- Облачная LLM используется только как fallback; чувствительность данных смет к внешнему LLM — вопрос к заинтересованным лицам (см. Open Questions).
- Очередь PDF-конвейера — таблица `spec_job` в Postgres; отдельный брокер сообщений не вводится.
- Модель эмбеддингов — `intfloat/multilingual-e5-small` (384 измерения, CPU).

## Open Questions

1. **Облачная LLM и данные** — **решено 2026-10-22:** облачные маршруты `llm-proxy` разрешены при явном согласии (`X-Allow-Cloud`) и аудите; payload без `structure_only` — осознанное исключение для chat-трафика (см. PRD Q1, AD-003).
2. **Типовые источники PDF**: из каких программ приходят сметы (ГРАНД-Смета, АВК-Смета и т.п.) — зависит от точности pdf-extract и покрытия метрики ≥ 95%.
3. **Объёмы**: сколько смет/позиций обрабатывает сметчик в день, размеры PDF — влияет на требования к очереди и параллелизму.
4. **Справочник расценок** — **решено 2026-10-24:** глобальный региональный справочник без `company_id` и без версий; региональная база 2022 и цены по кварталам/зонам; рассчитанные сметы защищены snapshot-полями (см. PRD Q4/Q8).
5. **Что такое «подраздел этапа»** — **решено 2026-10-20:** уровень «подраздел этапа» упразднён, сметы привязываются напрямую к этапу (см. PRD, Q5); гранулярность вводим заново только при реальной потребности.
6. **Порог 0.70:** остаётся открытым — подтверждается/калибруется на реальном корпусе после MVP.
