# smeta1 - Requirements Breakdown

## Overview

Данный документ содержит полную декомпозицию эпиков и историй для **smeta1** — системы автоматизации обработки строительных смет в цифровых PDF. Требования декомпозированы из PRD и Architecture Spine (AD-001..AD-008) в имплементируемые истории с критериями приёмки для разработчика.

## Requirements Inventory

### Functional Requirements

- FR-001: Авторизация и привязка пользователя к компании (по умолчанию новая компания). Публичная регистрация — `estimator`; `admin` — bootstrap.
- FR-002: Иерархия Компания → Договор (произвольная глубина) → Этап → Сметы. (2026-10-20: уровни «Подраздел этапа» упразднён — сметы привязываются к этапу.)
- FR-003: Загрузка цифрового PDF в S3 (MinIO) с валидацией (только цифровой PDF, ≤ 50 МБ).
- FR-004: Конвертация PDF → текст (pdfplumber/pypdfium2), без OCR.
- FR-005: LLM-извлечение спецификации (материал/работа, ЕИ, количество, раздел). Покрытие ≥ 95%.
- FR-006: Сопоставление позиций со справочником расценок по эмбеддингам с confidence (cosine 0–1); нормализация ЕИ. Поиск за точный регион/год/квартал/зону. Покрытие ≥ 90–95%.
- FR-007: Ручная проверка/исправление маппинга пользователем (полный UI — 1.1; API в MVP).
- FR-008: Импорт справочника расценок из Excel (.xlsx) с маппером колонок; региональная база 2022 и цены по кварталам/зонам.
- FR-009: Детерминированный расчёт детальной и итоговой стоимости (LLM не участвует).
- FR-010: Версии смет: несколько версий, ровно одна активная; готовность к diff (UI — 1.1).
- FR-011: Отображение детальной и итоговой стоимости в простом UI.
- FR-012: Аудит использования облачной LLM (attempt/fallback/denied/allowed).
- FR-013: Управление LLM-провайдерами/моделями и активной моделью компании; `api_key_env` без хранения ключей; аудит изменений.

### NonFunctional Requirements

- NFR-001: Локальная LLM — CPU-only, 8 ГБ ОЗУ, GGUF малых квантов q2–q3, без GPU.
- NFR-002: Гибрид local+cloud: `llm.allow_cloud_fallback=false` по умолчанию; `llm.redaction_mode=structure_only`; во внешнюю LLM только структурно-анонимизированные фрагменты.
- NFR-003: Поддержка только цифровых PDF (текстовый слой); OCR вне MVP.
- NFR-004: Стек: Python, FastAPI, Vue, Postgres + pgvector, MinIO (S3).
- NFR-005: Запуск локально через Docker Compose; готовность к Kubernetes.
- NFR-006: Время обработки 30–60с при локальной CPU-only модели (100–500 позиций).
- NFR-007: Объёмы MVP: 20–50 смет/месяц, 100–500 позиций/смета, PDF ≤ 50 МБ.
- NFR-008: Доля позиций с confidence < 0.70 ≤ 15% (цель).
- NFR-009: Расчёт 100% детерминирован (проверяется тестами).

### Additional Requirements

- AR-001: Snapshot расценок/ЕИ в позициях сметы (`rate_snapshot_id`, `unit_snapshot`, `rate_amount_snapshot`) — изменения справочника не влияют на рассчитанные версии (AD-002).
- AR-002: Договоры — adjacency list (`parent_id`), произвольная глубина (AD-006).
- AR-003: Обработка конвейера асинхронная; очередь — таблица `spec_job` в Postgres (`FOR UPDATE SKIP LOCKED`), отдельный брокер не вводится.
- AR-004: Микросервисные границы: api-gateway, auth-users, company-org, estimate, pdf-extract, spec-service, llm-proxy, llm-gateway, rate-catalog, s3/minio, ui, deploy.

## Epic 1: Базовая инфраструктура и безопасность LLM

Развернуть каркас микросервисов и llm-gateway с жёсткой политикой данных: локальный CPU-only рантайм (GGUF q2–q3, 8 ГБ ОЗУ), облачный fallback запрещён по умолчанию, разрешён только в режиме `structure_only` с аудитом. Обеспечить локальный запуск через Docker Compose и готовность к Kubernetes.

### Story 1.1: Каркас микросервисов и Docker Compose

As a разработчик,
I want единый каркас микросервисов, поднимаемый локально одной командой,
So that я мог разрабатывать и отлаживать сервисы независимо и согласованно.

**Acceptance Criteria:**

**Given** чистый репозиторий и установленный Docker Compose
**When** я запускаю `docker compose up`
**Then** поднимаются сервисы (api-gateway, auth-users, company-org, estimate, pdf-extract, spec-service, llm-proxy, llm-gateway, rate-catalog, ui) с healthcheck
**And** поднимаются Postgres и MinIO с персистентными томами
**And** конфигурация сервисов читается из переменных окружения

### Story 1.2: Локальный CPU-only LLM-рантайм (q2–q3, 8 ГБ ОЗУ)

As a сметчик,
I want локальную LLM, работающую без GPU на 8 ГБ ОЗУ,
So that система работала полностью локально на моём компьютере.

**Acceptance Criteria:**

**Given** машина с 8 ГБ ОЗУ и без GPU
**When** llm-gateway получает запрос на локальный инференс
**Then** используется GGUF-модель квантования q2–q3
**And** потребление памяти не превышает доступный лимит 8 ГБ ОЗУ
**And** запрос обрабатывается без обращения к GPU
**And** llm-gateway отдаёт единый интерфейс инференса вне зависимости от рантайма

### Story 1.3: Политика облачного fallback и аудит

As a владелец данных,
I want гарантию, что данные смет не утекают во внешнюю LLM без явного согласия,
So that конфиденциальность сметных данных соблюдалась.

**Acceptance Criteria:**

**Given** конфигурация по умолчанию
**When** система пытается выполнить облачный инференс
**Then** `llm.allow_cloud_fallback=false` блокирует запрос и фиксируется событие `denied`
**And** при `llm.redaction_mode=structure_only` во внешнюю LLM передаются только структурно-анонимизированные фрагменты (типы полей, схема), без наименований, количеств и ЕИ
**And** любое включение облачного fallback требует явного согласия и записывает событие аудита (timestamp, инициатор, причина, объём структурных блоков)
**And** все события (attempt/fallback/denied/allowed) сохраняются в журнале аудита

## Epic 2: Аутентификация, компании и иерархия договоров

Реализовать авторизацию с привязкой к компании (по умолчанию новая компания; `estimator` при регистрации, `admin` — bootstrap) и доменную иерархию: договоры произвольной глубины (adjacency list), этапы.

### Story 2.0 (внеплановая): Edge-слой api-gateway — JWT и identity-заголовки

As a владелец системы,
I want единственную точку входа с проверкой JWT,
So that внутренние сервисы не парсили токены и доверяли только identity-заголовкам.

**Acceptance Criteria:**

**Given** публичные пути `/v1/auth/register` и `/v1/auth/login`
**When** запрос идёт без токена
**Then** он проксируется в auth-users
**And** защищённые пути без валидного JWT получают `401 application/problem+json`
**And** gateway затирает входящие `X-User-Id`/`X-Company-Id`/`X-Role` и ставит их из проверенных claims
**And** неизвестный префикс — `404` без проверки токена

### Story 2.1: Авторизация и привязка к компании

As a сметчик,
I want авторизоваться и автоматически привязаться к компании,
So that я работал в изолированном пространстве своей организации.

**Acceptance Criteria:**

**Given** незарегистрированный пользователь
**When** он регистрируется впервые
**Then** создаётся новая компания и пользователь привязывается к ней
**And** роль пользователя — `estimator` (публичная регистрация); `admin` создаётся bootstrap-скриптом
**And** пользователь может войти и получить сессию/токен
**And** данные компании изолированы от других компаний

### Story 2.2: Договоры произвольной глубины (adjacency list)

As a сметчик,
I want создавать договоры с произвольной вложенностью,
So that отразить реальную структуру сотрудничества/подряда.

**Acceptance Criteria:**

**Given** авторизованный пользователь со своей компанией
**When** он создаёт договор с указанием `parent_id`
**Then** договор встраивается в иерархию на произвольную глубину
**And** циклы в иерархии запрещены (валидация)
**And** можно получить дерево договоров компании целиком

### Story 2.3: Этапы договора

As a сметчик,
I want привязывать этапы к договору,
So that сметы группировались по этапам работ.

**Acceptance Criteria:**

**Given** существующий договор
**When** пользователь создаёт этап
**Then** этап привязан к договору
**And** у одного договора может быть несколько этапов
**And** этапы доступны для последующей привязки смет

## Epic 3: Справочник расценок

Реализовать ведение справочника расценок: импорт только из Excel (.xlsx) с маппером колонок, региональная база 2022 и текущие цены по кварталам/зонам. Позиции смет ссылаются на snapshot расценок/ЕИ, поэтому изменения справочника не меняют уже рассчитанные версии смет.

**As-built (2026-10-25):** справочник глобальный и региональный; `rate_catalog`/`rate_catalog_version` не реализованы — Story 3.2 заменена Story 3.5. История 3.3 выполнена в рамках Epic 6.

### Story 3.1: Импорт справочника из Excel с маппером колонок

As a сметчик,
I want импортировать справочник расценок из Excel,
So that система использовала актуальные расценки для расчёта.

**Acceptance Criteria:**

**Given** файл `.xlsx` со справочником расценок
**When** пользователь загружает файл
**Then** система предлагает сопоставить колонки (наименование, ЕИ, цена/расценка и др.) через маппер
**And** импортируются только распознанные строки; некорректные строки помечаются с причиной
**And** форматы кроме `.xlsx` отклоняются

### Story 3.2: Версионирование справочника (не реализовано, заменено 3.5)

> **As-built 2026-10-25:** история не реализована. Таблиц `rate_catalog` и `rate_catalog_version` нет; импорт добавляет/обновляет `material`, `material_base_price`, `material_price` по естественному ключу, а неизменность смет обеспечивает snapshot (AR-001). Замена — Story 3.5.

As a сметчик,
I want видеть версии справочника,
So that понимать, на какой версии основан расчёт сметы.

**Acceptance Criteria:**

**Given** успешно импортированный справочник
**When** импорт завершается
**Then** создаётся `rate_catalog_version` (version, imported_at, source_file_hash, created_by)
**And** каждому пользователю/компании доступен единый справочник с историей версий
**And** можно получить текущую активную версию справочника

### Story 3.3: Snapshot расценок в позициях смет

As a сметчик,
I want, чтобы изменения справочника не искажали уже рассчитанные сметы,
So that результаты прошлых расчётов оставались воспроизводимыми.

**Acceptance Criteria:**

**Given** рассчитанная версия сметы с позициями
**When** импортируется новая версия справочника
**Then** позиции сохраняют `rate_snapshot_id`, `unit_snapshot`, `rate_amount_snapshot` на момент расчёта
**And** активная версия сметы и её стоимость не меняются
**And** повторный расчёт возможен только с явным выбором новой версии справочника

> **As-built 2026-10-25:** «новая версия справочника» заменена новым периодом/зоной. Рассчитанная версия сметы заморожена: чтобы получить новые цены, создаётся новая версия сметы, в неё импортируются позиции и заново подтверждаются.

### Story 3.4: Импорт сплит-формы индексов и сметных цен

As a сметчик,
I want импортировать реальные файлы ФСБЦ со сплит-формой,
So that не переделывать их вручную под формат КСР.

**Acceptance Criteria:**

**Given** `.xlsx` сплит-формы из 9 колонок с шапкой ниже заголовка/текста
**When** выполняется импорт
**Then** распознаются оба формата (КСР и сплит-форма), все 9 колонок сохраняются
**And** `rate_amount = base_estimate_price × index_value`; при отсутствии индекса используется текущая цена
**And** строка нумерации `1…9` пропускается, невалидные строки попадают в `rejected`
**And** лимита на число строк данных нет; ограничение — файл ≤ 20 МБ

### Story 3.5: Региональная база 2022 и цены по кварталам/зонам

As a сметчик,
I want вести справочник в разрезе регионов, кварталов и ценовых зон,
So that цены соответствовали реальной структуре данных.

**Acceptance Criteria:**

**Given** импорт с регионом/годом/кварталом/зоной
**When** файл обработан
**Then** материал уникален по `(region_code, code)`, база 2022 хранится в `material_base_price`, текущая цена — в `material_price` по `(material_id, year, quarter, zone_code)`
**And** повторный импорт другого квартала добавляет новую цену, переиспользуя региональную базу
**And** `estimate` хранит зону периода и передаёт её в сопоставление
**And** старый формат КСР продолжает поддерживаться

## Epic 4: Загрузка и извлечение цифрового PDF

Реализовать загрузку цифрового PDF-сметы в MinIO с валидацией и конвертацию PDF → текст без OCR. Поддерживаются цифровые PDF (ГРАНД-Смета, АВК-Смета, совместимые).

### Story 4.1: Загрузка цифрового PDF в MinIO с валидацией

As a сметчик,
I want загружать PDF-смету,
So that система могла извлечь из неё спецификацию.

**Acceptance Criteria:**

**Given** авторизованный пользователь
**When** он загружает PDF-файл
**Then** файл сохраняется в MinIO (S3), создаётся запись `file` (storage_key, mime_type, size, meta)
**And** файлы > 50 МБ отклоняются с понятной ошибкой
**And** файлы без текстового слоя (сканы) отклоняются как неподдерживаемые (OCR вне MVP)

### Story 4.2: Конвертация PDF → текст (без OCR)

As a сметчик,
I want получать текстовое представление загруженной сметы,
So that LLM могла извлечь из него спецификацию.

**Acceptance Criteria:**

**Given** загруженный цифровой PDF с текстовым слоем
**When** срабатывает pdf-extract
**Then** извлекается текст с сохранением структуры строк/таблиц (pdfplumber/pypdfium2)
**And** результат сохраняется и передаётся в конвейер как артефакт
**And** покрытие извлечения для типовых PDF ГРАНД-Смета/АВК-Смета ≥ 95% (проверка на тестовом наборе)

## Epic 5: Извлечение спецификации и маппинг с confidence

Реализовать LLM-извлечение спецификации (материал/работа, ЕИ, количество, раздел) через local-first LLM, сопоставление со справочником расценок с confidence и нормализацией ЕИ, а также API ручной проверки. Полный UI валидации — 1.1.

**As-built 2026-10-25:** извлечение — `spec-service` через `llm-proxy` → `llm-gateway`; сопоставление — `rate-catalog` по эмбеддингам (Story 8.1), не LLM; сохранение и ручная проверка — `estimate`.

### Story 5.1: LLM-извлечение спецификации (local-first)

As a сметчик,
I want автоматически получать спецификацию из текста сметы,
So that не переносить позиции вручную.

**Acceptance Criteria:**

**Given** текстовый артефакт извлечённой сметы
**When** вызывается llm-spec через llm-gateway
**Then** формируется список позиций: материал/работа, ЕИ, количество, раздел сметы
**And** используется локальный CPU-only рантайм (local-first)
**And** облачный fallback не применяется, если не разрешён (AD-003)
**And** покрытие извлечения позиций ≥ 95% на типовых цифровых PDF

> **As-built 2026-10-25:** извлечение вынесено в `spec-service` (асинхронная задача `spec_job`), вызов модели — через `llm-proxy` (alias → local/cloud), артефакты `chunks/*` и `specification.json` — в MinIO.

### Story 5.2: Маппинг со справочником и нормализация ЕИ с confidence

As a сметчик,
I want видеть сопоставление позиций со справочником и уверенность модели,
So that быстро проверить результат и найти проблемные места.

**Acceptance Criteria:**

**Given** извлечённая спецификация и активная версия справочника
**When** выполняется маппинг
**Then** для каждой позиции предлагается сопоставление с расценкой и нормализованная ЕИ
**And** каждой позиции присваивается `confidence` (0–1)
**And** позиции с `confidence < 0.70` помечаются как требующие проверки
**And** доля позиций с `confidence < 0.70` ≤ 15% на тестовом наборе

> **As-built 2026-10-25:** «активная версия справочника» заменена периодом (регион/год/квартал/зона). Сопоставление выполняет `rate-catalog` по эмбеддингам (AD-016), `estimate` сохраняет результат; `confidence` — cosine score, LLM не участвует.

### Story 5.3: API ручной проверки маппинга

As a сметчик,
I want подтверждать или исправлять сопоставления,
So that итоговый расчёт опирался на проверенные данные.

**Acceptance Criteria:**

**Given** позиции с предложенным маппингом
**When** пользователь подтверждает или изменяет сопоставление через API
**Then** статус и выбранная расценка/ЕИ сохраняются в позиции
**And** низкоуверенные позиции выделяются в ответе API
**And** полный UI валидации маппинга помечен как 1.1 (вне данной истории)

## Epic 6: Версионирование смет и детерминированный расчёт

Реализовать сметы с версиями (несколько, ровно одна активная), готовность к diff, а также детерминированный расчёт детальной и итоговой стоимости на основе snapshot-значений.

### Story 6.1: Создание сметы и версий (ровно одна активная)

As a сметчик,
I want вести сметы с несколькими версиями,
So that хранить историю и работать с актуальной редакцией.

**Acceptance Criteria:**

**Given** существующий этап договора
**When** пользователь создаёт смету
**Then** создаётся смета с первой версией (`estimate_version`)
**And** у сметы может быть несколько версий, но ровно одна `is_active=true`
**And** при активации новой версии предыдущая деактивируется атомарно
**And** структура версий хранит позиции (`estimate_item`) и снапшоты, достаточные для будущего diff

### Story 6.2: Готовность к diff между версиями

As a сметчик,
I want, чтобы данные позволяли сравнить версии сметы,
So that видеть изменения между редакциями (UI diff — 1.1).

**Acceptance Criteria:**

**Given** две версии одной сметы со своими позициями
**When** запрашивается вычисление различий на уровне API
**Then** возвращаются добавленные/удалённые/изменённые позиции (по количеству, ЕИ, расценке)
**And** сравнение опирается на сохранённые снапшоты, без повторного расчёта
**And** UI-представление diff помечено как 1.1 (вне данной истории)

### Story 6.3: Детерминированный расчёт стоимости

As a сметчик,
I want получать детальную и итоговую стоимость сметы,
So that использовать проверяемые цифры.

**Acceptance Criteria:**

**Given** активная версия сметы с подтверждёнными сопоставлениями и снапшотами
**When** выполняется расчёт в estimate
**Then** детальная стоимость по позициям и итоговая стоимость рассчитываются по фиксированным формулам
**And** расчёт не использует LLM и полностью детерминирован (одинаковый вход → одинаковый выход)
**And** результат сохраняется в версии сметы с отметкой времени расчёта
**And** покрывается тестами на детерминизм

## Epic 8: Семантическое сопоставление позиций (as-built)

Реализовать автоматическое сопоставление позиций сметы со справочником цен по эмбеддингам наименований. Эпик появился после Epic 7 и не входил в исходное планирование.

### Story 8.1: Сопоставление позиций сметы со справочником цен по эмбеддингам

As a сметчик,
I want автоматически получать расценку для каждой позиции,
So that не искать её вручную и сразу видеть стоимость.

**Acceptance Criteria:**

**Given** активная нерассчитанная версия сметы и период (регион/год/квартал/зона)
**When** вызывается `POST /v1/estimates/{id}/versions/{vid}/match-rates`
**Then** `rate-catalog` по E5-эмбеддингам возвращает ближайшую цену за точный период/зону
**And** `estimate` сохраняет `rate_catalog_id`, `rate_code`, `confidence` (cosine 0..1, 4 знака) только у `proposed`-позиций
**And** `confirmed`/`corrected` не перезаписываются и попадают в `skipped`
**And** ненайденные позиции очищаются (`rate_catalog_id=null`, `confidence=0`)
